# Clicker 安卓连点器 — 项目设计文档

> 版本：v0.1（设计稿，尚未进入编码）
> 日期：2026-11-16
> 状态：需求分析完成，待开发

---

## 1. 项目定位

一款**离线、零 root、最小权限**的安卓手机连点器，通过系统无障碍服务模拟屏幕点击与滑动手势，支持多步手势序列、取点辅助与拟人化随机参数，最终打包为可独立安装的 APK。

---

## 2. 核心诉求与约束

| 诉求 | 说明 | 技术约束 |
|---|---|---|
| 离线可用 | 无网络也能运行 | 不申请 `INTERNET`，不做联网校验 |
| 最小化权限 | 尽量少申请权限 | 最终仅 1 项悬浮窗权限 + 无障碍授权 |
| 打包 APK | 独立安装到手机 | 原生 Android 工程，release 签名产出 |
| 无 root | 普通用户可直接用 | 依赖无障碍服务，而非 root 注入 |
| 进阶能力 | 多步序列 + 滑动 + 取点 | 统一的手势序列模型 |
| 拟人化 | 降低机械规律特征 | 随机偏移 / 抖动 / 速度曲线等参数 |

---

## 3. 技术选型

| 决策点 | 选择 | 理由 |
|---|---|---|
| 开发语言 | Kotlin | 官方首选，与 Android 无障碍 API 配合最佳 |
| 点击注入 | AccessibilityService + dispatchGesture | 唯一满足「无 root + 离线 + 独立运行」的合法方案 |
| 悬浮控制 | SYSTEM_ALERT_WINDOW 悬浮窗 | 悬浮球 + 控制面板 + 取点辅助 |
| 本地存储 | SharedPreferences / Room | 应用私有目录，无需存储权限 |
| 最低系统 | Android 7.0（API 24） | 覆盖绝大多数机型 |

### 3.1 为什么选无障碍服务（而非其他方案）

| 方案 | root | 需电脑 | 可独立运行 | 结论 |
|---|---|---|---|---|
| 无障碍服务 | 否 | 否 | 是 | ✅ 首选 |
| 悬浮窗 + 普通点击 | 否 | 否 | 是 | ❌ 普通应用无法跨应用注入点击 |
| root + 底层注入 | 是 | 否 | 是 | ❌ 违背最小权限诉求 |
| ADB 调试注入 | 否 | 是 | 否 | ❌ 不能脱离电脑使用 |

## 4. 权限设计（最小化）

最终 Manifest 中仅声明 **1 项** 权限：

| 能力 | 系统机制 | Manifest 权限 | 危险权限 |
|---|---|---|---|
| 模拟点击/滑动 | 无障碍服务 | 无需声明 | 否（用户手动授权） |
| 悬浮球 / 取点 | SYSTEM_ALERT_WINDOW | 需声明 | 是（需引导授权） |
| 配置持久化 | 应用私有目录 | 无需声明 | 否 |

**明确不申请**：`INTERNET`、存储读写、定位、电话、通讯录等。

### 4.1 两个独立开关（关键）

- **无障碍服务**：用户去「设置 → 无障碍」手动开启，用于实际点击。
- **悬浮窗**：运行时权限，用于悬浮球与取点辅助。

两者独立。App 需提供**权限引导页**，逐一检测并跳转对应系统设置页。

## 5. 系统架构

```
Clicker (Android 项目)
├── accessibility/          # 无障碍服务（核心引擎）
│   └── ClickerService       # 接收指令 → 注入点击/滑动
├── overlay/                # 悬浮窗（控制面板 + 取点）
│   ├── FloatingBallService  # 悬浮球（拖拽、点击展开面板）
│   ├── ControlPanel         # 展开后的控制面板（启动/暂停/停止）
│   └── PointPickerOverlay   # 取点辅助悬浮层（显示坐标）
├── engine/                 # 连点引擎（纯逻辑，不依赖 UI）
│   ├── ClickTask            # 任务定义
│   ├── TaskScheduler        # 调度器：循环、定时、次数控制
│   ├── GestureBuilder       # 把「步骤」变成手势描述（含随机化）
│   └── Randomizer           # 拟人化随机参数生成器
├── config/                 # 配置持久化
│   └── TaskStore            # 保存/读取任务配置
├── ui/                     # 主界面
│   ├── MainActivity         # 任务列表 + 新建/编辑
│   ├── PermissionGuide      # 权限引导页
│   └── TaskEditor           # 任务编辑器
└── util/
    └── ScreenMetrics        # 分辨率、密度换算
```

## 6. 核心数据模型

### 6.1 手势步骤（Step）

```
Step
├── type      : TAP（点击）/ SWIPE（滑动）/ DELAY（等待）
├── x, y      : 基准坐标（TAP / SWIPE 起点）
├── x2, y2    : 终点坐标（仅 SWIPE）
├── duration  : 持续时间（SWIPE 滑动耗时 / DELAY 等待时长）
```

### 6.2 连点任务（Task）

```
Task
├── 基础配置
│   ├── name            任务名
│   ├── steps[]         手势步骤序列（按顺序执行）
│   └── loop            循环模式（固定次数 / 无限）
│
├── 坐标层
│   ├── 每步 x, y       基准坐标
│   └── 滑动 x2,y2      终点坐标
│
├── 节奏层（点击速度）
│   ├── interval        步骤间隔（基准值）
│   ├── intervalJitter  间隔随机浮动范围（如 ±50ms）
│   └── duration        滑动耗时 / 等待时长
│
├── 拟人化层（防检测）
│   ├── coordJitter     坐标随机偏移范围（如 ±3px）
│   ├── pressTime       按压时长（真实手指按下→抬起）
│   ├── pressTimeJitter 按压时长浮动
│   ├── speedCurve      滑动速度曲线（匀速 / 缓起缓停）
│   └── randomPause     随机停顿休息
│
└── 安全层
    ├── stopOnScreenChange   屏幕内容变化时自动暂停
    └── emergencyStop        紧急停止
```

> 设计要点：**单点连点只是「1 个 TAP step + interval」的特例**，多点连点、点滑结合都是同一模型，无需为每种玩法单独写逻辑。

## 7. 拟人化（防检测）设计

### 7.1 定位边界

「防检测」本质是**让点击行为更接近真人手指**，降低被目标 App 静态行为规律识别的概率。它是「拟人化随机」，**不是**「绕过安全机制」。

| 检测方 | 机制 | 应对 |
|---|---|---|
| 目标 App 自动化风控 | 检测间隔规律、坐标固定、轨迹机械 | 随机化参数 ✅ |
| 系统无障碍授权 | 用户主动授权的合法能力 | 无需规避 |

### 7.2 各参数作用原理

| 参数 | 作用 | 原理 |
|---|---|---|
| coordJitter | 坐标随机偏移 | 真实手指不会每次点同一像素，打破坐标恒定特征 |
| intervalJitter | 间隔抖动 | 打破恒定间隔的单一频率特征 |
| pressTime | 按压时长 | 真实触摸有 50~150ms 接触时长，非瞬点 |
| speedCurve | 滑动速度曲线 | 真人滑动「先加速后减速 + 轻微弧度」，非匀速直线 |
| randomPause | 随机停顿 | 模拟「累了歇一下」，进一步打散规律 |

### 7.3 随机化 vs 可控性的权衡

- 随机化越强 → 越难检测，但越不可预测（可能点错位置 / 节奏失控）。
- 用户要的是**可控的拟人化**。

**设计原则**：所有随机参数都提供「基准值 + 浮动范围」两个旋钮；提供「拟人化开关」一键套用推荐值，高级用户再手动微调。

### 7.4 诚实的边界

1. 随机化降低**基于行为规律的静态检测**，但无法绕过目标 App 对「无障碍服务是否开启」的系统级判定。
2. 专业反外挂（行为分析 + 设备指纹 + 服务端风控）仍可能识别，**没有「绝对防检测」**。
3. 本项目承诺「显著降低机械规律特征、提供可调参数」，不承诺「保证不被发现」。此边界将写入 App 说明。

## 8. 技术难点与坑

| # | 难点 | 说明 |
|---|---|---|
| 1 | 点击延迟抖动 | dispatchGesture 异步注入，真实频率上限约 10 次/秒，UI 需限制最大频率 |
| 2 | 坐标与屏幕密度 | 无障碍手势用物理像素；任务配置同机准确，换机可能错位（固有限制） |
| 3 | 取点辅助 | 悬浮层「拦截触摸」与「透传触摸」矛盾，需权衡（见 9） |
| 4 | 系统回收 | 低电量/后台限制可能回收无障碍服务，需引导加入电池优化白名单 |
| 5 | 国产 ROM 适配 | MIUI/EMUI 无障碍入口深、有「后台弹出界面」限制，需 ROM 引导 |
| 6 | 悬浮球拖拽 vs 点击 | 需拖动距离阈值区分（如 <5px 算点击，否则拖拽） |

---

## 9. 取点辅助方案

两种方案，**推荐 B 优先做，A 作为增强**：

- **A. 触摸透传取点**：透明悬浮层显示坐标 + 目标 App 仍可被操作。实现复杂（需解决透传矛盾）。
- **B. 独立取点页**：手指在取点页移动读坐标，再输入到任务。实现简单、稳定。✅ 推荐

---

## 10. 开发里程碑

1. **M1（最小可运行闭环）**：骨架工程 + 权限引导页 + 无障碍服务 + 单点连点（带基础随机参数）+ 悬浮球控制。目标：真机验证「能点、能停、参数生效」。
2. **M2**：任务引擎进阶（多步序列、滑动、间隔、循环/次数）。
3. **M3**：取点辅助。
4. **M4**：配置持久化 + 任务列表 UI。
5. **M5**：打包 release APK（签名、离线、权限精简核对）。

---

## 11. 最终结论

- **技术栈**：Kotlin + 无障碍服务 + 悬浮窗
- **权限**：仅 1 项悬浮窗权限 + 无障碍授权，离线，无网络
- **能力**：多步序列 + 滑动 + 取点辅助 + 拟人化随机参数
- **边界**：拟人化 ≠ 绝对防检测
